02The repository is the system

The claim that defines production-grade here: tear the account down, run agentcore deploy from the repo, and everything returns. That holds only because each piece lives in a declared file:

Anti-pattern we committed, then reversed

The LTM strategy was first attached by a hand-run API script (update_memory from a terminal). It worked — and left the stack believing strategies: [] while reality had one. Config drift: unreproducible for a teammate, and a future collision for CloudFormation. The fix was to delete the hand-attached strategy, declare it in agentcore.json, and let the deploy recreate it. VERIFIED — the declared path produced a working strategy end to end.

The test for any script: who calls it? If the answer is "a person, once," it belongs in declared config.

Both loops land on the same Runtime service — the platform doesn't care whether the bundle came from a zip or an image. What separates them is reproducibility: the zip resolves dependencies on a laptop at deploy time; the image is built once, scanned, digest-pinned, and promoted untouched. Local testing exercises your logic; only a cloud deploy exercises the platform contract — IAM as the execution role, linux/arm64 dependency resolution, session isolation, the real invocation envelope. VERIFIED — three of our four first-deploy failures were platform-contract errors invisible locally.

04Invocation path

Production callers use the data-plane API with IAM auth. This is the path we verified everything through:

client = boto3.client("bedrock-agentcore", region_name="us-east-1")
r = client.invoke_agent_runtime(
    agentRuntimeArn=RUNTIME_ARN,
    runtimeSessionId=session_id,          # ≥33 chars; your session key
    payload=json.dumps({
        "prompt": "What is the weather in Pune?",
        "user_id": "priya",               # custom fields pass through verbatim
        "thread_id": "conversation-3",
    }).encode(),
)
Tooling caveat

The npm CLI's agentcore invoke rewraps the payload and silently drops custom fields — our user_id vanished, and memory keyed itself on session IDs instead of users. VERIFIED by reading the memory service's actor list. Use the CLI for smoke tests of prompt only; anything with a payload contract goes through the SDK.

05Memory: one interface, two tiers, two writes

LangGraph and AgentCore Memory are layers, not rivals. LangGraph's checkpointer is the interface (save/load conversation state under a thread_id); AgentCore Memory is a durable backend for it, plus an extraction service no in-process library offers.

──▶

files notes → /users/{actorId}

Read side, per request: fetch this user's notes by relevance (retrieve_memory_records), inject as a system message, invoke the graph with thread_id (the conversation) and actor_id (the user).

  • VERIFIED STM survives process death and microVM boundaries — conversation recalled across cloud sessions.
  • VERIFIED LTM crosses conversations — "prefers Celsius" taught in one thread converted 72°F→22°C in a brand-new thread; a control user still got Fahrenheit.
  • VERIFIED Extraction is asynchronous (~2 min) and processes only conversational events. Checkpointer blobs are invisible to it — hence the double-write. This is a real integration gap, not a design choice you'd make freely.
Design note

The same conversation is stored twice, in two formats. An agent built directly on the Memory API (e.g. Strands without a checkpointer) writes only conversational events and uses them for both replay and extraction. The double-write is the price of LangGraph's checkpointer snapshotting its own state format. Budget for it or choose accordingly.

06Tutorial habits that don't survive production

  • ANTI-PATTERN Hand-run setup scripts. Anything a person runs once against the control plane is invisible drift. Promote it to declared config.
  • ANTI-PATTERN Auto-created IAM roles. The toolkit's execution role is broad by design. Production declares a least-privilege role: bedrock:InvokeModel on named models, the memory ARN, its own log group — nothing else. (Still open debt in this build.)
  • ANTI-PATTERN Swallowing infrastructure exceptions. Our try/except: pass around memory writes turned a missing required parameter into a ten-minute mystery. Degrade gracefully, but log every suppressed failure.
  • DEV-ONLY Zip (direct code) deploys. Dependencies resolved on a laptop at deploy time. Fine for sandboxes; prod promotes a digest-pinned image.
  • DEV-ONLY CLI invocation. See §04 — the payload contract isn't honored.
  • DEV-ONLY Config clicked into consoles or UIs. Reproducible systems have no memory of hands.
  • DEV-ONLY In-process memory (MemorySaver). Every tutorial's default. State dies with the microVM; in production it's an illusion of memory.

07Open debt in this build

Honest gaps between this system and one you'd sign off for production traffic:

  • Least-privilege execution role, declared in the stack (currently the toolkit's broad auto-created role).
  • Environment promotion — one environment exists; test/nonprod/prod with the same declared config and per-env variables is designed (§03) but not stood up.
  • Caller authorization design — IAM works; a real product decides between IAM and OAuth on the endpoint deliberately.
  • Observability pass — logs and OTEL ship, but X-Ray trace delivery needs an account-level destination fix, and nobody has read the dashboards in anger yet.
  • Real tool — get_weather is a stub; a live API brings egress, secrets, and failure handling into scope.
